# BUG-044 - IP do cliente vinha de cabeçalho que o próprio cliente podia forjar

- **ID:** BUG-044
- **Data:** 2026-10-16
- **Severidade:** MÉDIA (afeta o rate limit, os sinais antifraude e os registros de aceite/LGPD)
- **Perfil afetado:** todos

## Passos para reproduzir
1. Chamar a API mandando `CF-Connecting-IP`, `X-Real-IP` ou `X-Forwarded-For` com valores inventados.
2. O rate limit e o antifraude usavam esses valores. Alguns pontos (aceite legal, LGPD, convite de conta) usavam o `X-Forwarded-For` escrito pelo cliente.

## Causa raiz
Não existe nginx: o tráfego entra pelo Cloudflare Tunnel (cloudflared, local), passa pelo gateway `app/web/gateway.mjs` (local) e chega à API. O gateway repassava os cabeçalhos do cliente e definia `x-real-ip` com o endereço do cloudflared (127.0.0.1). A API confiava em `cf-connecting-ip`/`x-real-ip` vindos de qualquer origem. Por isso todos os clientes caíam no mesmo IP, ou o próprio cliente escolhia o IP.

## Correção (arquivos alterados)
- `app/api/clientip.js` (novo): `cf-connecting-ip` só vale quando o socket é loopback (veio do gateway local). Fora disso vale o endereço do socket. O `X-Forwarded-For` é sempre ignorado. `TRUST_PROXY=off` desliga a confiança.
- `app/web/gateway.mjs`: `proxyHeaders()` descarta `X-Forwarded-For`, `X-Real-IP` e `CF-Connecting-IP` do cliente. Repassa o `cf-connecting-ip` só quando ele vem do cloudflared local e escreve `x-real-ip`/`x-forwarded-for` limpos.
- `server.js`, `billing/routes.js`, `legal.js`, `lgpd.js`, `accounts-v42.js`, `referral.js`, `monetization-admin.js`: todos passam a usar `clientIp()`.

## Teste de regressão adicionado
`app/api/test/v6-clientip.mjs` (7 casos: gateway local, conexão direta, X-Forwarded-For, valor inválido, TRUST_PROXY=off e os cabeçalhos do gateway).

## Lição / armadilha
Confiar só no cabeçalho que o nosso próprio proxy escreve e só quando a conexão vem dele.
